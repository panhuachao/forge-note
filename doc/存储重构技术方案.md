# 锦囊笔记存储重构技术方案

> 配套文档：`doc/存储实现方案.md`。
> 目标：基于现有实现，从**稳定性**（崩溃安全、数据不丢、索引不崩）与**扩展性**（知识库变大、多知识库、向量检索、增量更新）两方面，给出可落地的重构路线。
> 每项均标注：现状问题 → 重构方案 → 影响面 → 优先级。

---

## 0. 现状基线（已验证）

| 层 | 现状 | 风险点 |
| --- | --- | --- |
| 笔记正文 | `fs-service` + `atomicWrite`（临时文件+rename） | 已较稳；跨进程并发无锁 |
| 检索索引 | `search-service` 纯内存 `Map<kbId,{entries,ts}>`，`Set` 分词，60s 过期全量 `walk` 重建；**不落盘** | 重启即失；大库每次 60s 一次全目录扫描；仅 2MB 截断；无标签/反链检索 |
| 双向链接 | `link-index` 纯内存，`Map<kbId,Map<path,Set>>` | 重启依赖重扫；无持久化 |
| SQLite | `better-sqlite3` WAL，仅 `kbs/app_config/ai_presets/audit` 四表 | 未承载检索/链接/笔记元数据，能力闲置 |
| AI 会话 | `.AI_TALK/<convId>.json` 文件 + `index.json` | 文件化易调试，但无事务、无查询能力 |
| `kb_list_notes` 时间窗口 | 每次调用 `walkRecentNotes` 全目录递归过滤 mtime | 大库慢、重复 IO |

## 1. 检索索引持久化与 FTS5 升级（最高优先级 · 稳定性+扩展性的交汇点）

### 1.1 现状问题
- 索引**纯内存、不落盘**：进程重启（或 dev HMR）后整库重扫，大库冷启动慢、首搜卡顿。
- `query` 在 `Date.now()-ts>60_000` 时**同步触发全目录 `walk`**（`await reindex`），搜索请求被阻塞。
- 分词仅 `Set` 词面匹配：中文按 2 字 N-gram、英文按词，无位置/权重/标签字段，**不支持短语、标签、反链维度检索**。
- 单篇 >2MB 直接跳过，长笔记不可搜。

### 1.2 重构方案
1. **索引落 SQLite（FTS5）**：新建表 `note_index`，与现有 `config.db` 同库（复用 WAL），或独立 `search.db`：
   ```sql
   CREATE VIRTUAL TABLE IF NOT EXISTS note_index USING fts5(
     kb_id UNINDEXED,
     note_path UNINDEXED,
     note_name UNINDEXED,
     template_dir_id UNINDEXED,
     title,            -- 标题/文件名，权重高
     body,             -- 正文
     tags,             -- #标签
     tokenize = 'unicode61'
   );
   -- 元数据（mtime / size / 反链数）用普通表，避免 FTS 行外字段
   CREATE TABLE note_meta (
     kb_id TEXT, note_path TEXT,
     mtime INTEGER, size INTEGER, template_dir_id TEXT,
     link_count INTEGER DEFAULT 0,
     PRIMARY KEY (kb_id, note_path)
   );
   ```
2. **增量更新**：`fs.watch` 事件（`add/unlink/change`）只对该 `note_path` 做 `INSERT/DELETE`（FTS5 `DELETE WHERE rowid=...` + `INSERT`），不再全量重建。`reindex` 仅作为手动/首次全量入口。
3. **异步化**：`query` 不再在请求路径上触发 `reindex`；改为启动时后台预热 + 监听事件增量维护，查询始终命中已建索引。
4. **检索维度增强**：`title` 列加权（FTS5 `bm25(note_index, 10.0, 1.0)` 让标题权重 10×）；`tags` 独立列支持 `#标签` 检索；`kb_search` 增加 `matchType` 区分。
5. **长笔记分块**：>2MB 笔记按段落切分多行写入 `note_index`（带 `rowid` 分片），避免不可搜。

### 1.3 影响面
- `search-service.ts` 整体重写查询层；`IndexEntry` 接口废弃。
- `kb-service.buildTree` 不再顺带重建检索；改为 `fs.watch` 驱动。
- `ai-service.rerankHits` 不变（在召回结果上重排，与索引实现解耦）。
- `tool-runtime.kb_search` 调用签名不变。

### 1.4 优先级：P0（直接消除重启全扫 + 搜索阻塞两大稳定性隐患）

## 2. 双向链接索引持久化（稳定性）

### 2.1 现状问题
`link-index` 纯内存，`Map<kbId,Map<path,Set<target>>>`。重启后依赖整库重扫重建；若重扫遗漏（如隐藏目录边界）会导致反链面板短暂为空。

### 2.2 重构方案
- 与检索索引同生命周期：在 `note_meta.link_count` 之外，新增 `note_links(kb_id, note_path, target)` 表，保存出链关系。
- `fs.watch` 的 `change/unlink/rename` 事件同步维护该行表（与 FTS 更新同一事务）。
- `linkIndex.resolve / getBacklinks` 改为优先读 SQLite，内存仅作热缓存。
- 启动时由 FTS/`note_meta` 一次性加载到内存（O(笔记数) 行，远快于全目录 walk）。

### 2.3 影响面
`link-index.ts` 改为「SQLite 真源 + 内存缓存」双写；`resolve`/`getBacklinks` API 不变。

### 2.4 优先级：P1

## 3. 笔记元数据独立索引（扩展性）

### 3.1 现状问题
- `kb_list_notes(sinceDays)` 每次调用 `walkRecentNotes` 递归整目录按 mtime 过滤，大库重复 IO。
- `frontmatterService` 解析 `createdAt/updatedAt` 需读文件+parse，列表/排序场景昂贵。
- 无法按标签、目录、时间区间做组合查询。

### 3.2 重构方案
- 复用 `note_meta(mtime, size, template_dir_id, link_count)` + 新增 `created_at`、`tags`（JSON 或 `note_tags` 关联表）。
- `kb_list_notes` 改为 SQL：`SELECT note_path, mtime FROM note_meta WHERE kb_id=? AND mtime>=? ORDER BY mtime DESC LIMIT ?`，O(索引) 而非全目录。
- 标签检索走 `note_tags(kb_id, note_path, tag)` 关联表，支撑组合过滤（`dir + tag + 时间`）。
- 写入/重命名经 `fs.watch` 同步维护，无需扫描。

### 3.3 影响面
`tool-runtime.kb_list_notes` 内部实现替换；`kb-service` 目录树可复用 `note_meta.template_dir_id` 做分类。

### 3.4 优先级：P1（扩展性的关键，使时间/标签检索可扩展到大库）

## 4. frontmatter 与正文写入的一致性（稳定性）

### 4.1 现状问题
- `writeNote` 同时改文件 + 改 `search-service` 内存 + 改 `link-index` 内存，三步非事务，**任一步失败会导致索引与文件不一致**（如文件写成功但索引未更新，搜索结果陈旧）。
- 多窗口/外部编辑器改文件时，依赖 `fs.watch` 但 watch 在部分文件系统（网络盘、容器挂载）会丢事件。

### 4.2 重构方案
1. **单入口写通道**：所有笔记写操作经 `fs-service.writeNote`，在该函数内以「文件原子写成功 → 再更新 SQLite(note_index + note_meta + note_links)」的顺序提交；失败回滚（删临时文件）。
2. **校验与自愈**：启动时对 `note_meta` 与文件系统做一次轻量对账（`mtime` 不一致则增量重建该篇），兜底 watch 丢事件。
3. **防竞态**：同一 `note_path` 的写/索引更新串行化（per-path 队列），避免并发 `rename` 导致索引错位。

### 4.3 影响面
`fs-service.writeNote/moveNote/deleteNote` 内聚索引维护；`search-service/link-index` 暴露「单篇 upsert」方法供其调用。

### 4.4 优先级：P0（直接修复索引/文件不一致这一核心稳定性缺陷）

---

## 5. AI 会话存储评估与可选统一（扩展性）

### 5.1 现状
会话以 `.AI_TALK/<convId>.json` 文件存储，每轮 `atomicWrite` 整文件覆写。`clearHistory` 即删文件。

### 5.2 重构方案（可选，非必须）
- **保留文件化**（利于随知识库备份/迁移、易调试），但做两点增强：
  - 增量追加：将 `turns` 改为**追加写**（`appendTurn` 只写新 turn，不重写全量），大会话避免每次全文件序列化。
  - 会话元数据（标题/时间/首轮摘要）单独 `sessions_meta.json`，列表加载不读全文。
- **或统一入 SQLite**（若未来需要跨知识库检索/分析对话）：`ai_turns(conv_id, idx, role, text, ts, refs_json, tool_json)`，沿用现有 WAL 与事务。

### 5.3 决策建议
V1.x 维持文件化 + 追加写（低成本、稳定性足够）；仅在需要「对话级检索/审计」时迁 SQLite。本方案倾向**追加写增强**，不在本次强制重构。

### 5.4 优先级：P2（可选）

## 6. 多知识库与隔离（扩展性）

### 6.1 现状问题
- 所有 KB 共享同一个 `config.db`，`kbs` 表以 `id` 区分；检索/链接索引以 `kb_id` 为键，逻辑隔离 OK。
- 但 `note_index` 若放 `config.db`，单库体积随笔记增长膨胀，备份/迁移单个知识库困难。

### 6.2 重构方案
- **按知识库分库**（推荐）：每个 KB 在 `rootPath/.forgenote/index.db`（隐藏、随库迁移）持有该库的 `note_index / note_meta / note_links / ai_turns`。`config.db` 仅留 `kbs` 注册信息与全局 `app_config`。
- 好处：知识库拷贝即带走全部索引与对话；单库损坏不影响其他库；可并行独立 reindex。
- 打开 KB 时 `attach` 其 `index.db`；关闭/卸载时 `detach`。

### 6.3 影响面
`store.ts` 拆分为「全局库 + 每库索引库」两层；`search-service/link-index/session-store` 的 `kbId` 维度改为「打开对应 index.db」。

### 6.4 优先级：P2（规模化前的架构铺垫）

---

## 7. 检索/向量底座（扩展性）

### 7.1 现状
纯关键词/BM25，无语义检索。`ai-service.rerankHits` 已是轻量重排，但召回阶段无语义。

### 7.2 底座职责（向量归属 RAG 流水线，见 §8）
- FTS5 负责**关键词/短语/标签**召回（BM25 排序）。
- 向量召回（embedding）作为 RAG 流水线的独立环节，在 §8 统一设计，不在本节重复。

### 7.3 接口稳定性
`kb_search` 与 `ai-service.ask*` 的**对外契约保持不变**，索引/向量化仅在召回层内部替换，不影响上层 skill/路由。

### 7.4 优先级：P3（底座为增强项，非稳定性必需）

---

## 8. RAG 流水线专项重构（稳定性 + 扩展性核心）

### 8.1 现状问题（已验证）
当前 RAG 实现为「召回 → 重排 → 注入」三段，存在以下短板：

1. **无分块（chunk）**：`ask` 走关键词召回后直接注入 `SearchResult.snippet`（检索时缓存的**前 8KB 正文**）；`runTimeSummary`（时间维度总结）则 `kb_list_notes` 列出路径后逐篇 `kb_read_note` 整篇读取，单篇 `slice(0, 2000)` 截断、总计 `24000` 字封顶。长笔记被暴力截断，信息丢在「中部/尾部」。
2. **召回仅关键词**：`searchService.query` 是词面匹配 + `rerankHits` 词面重叠加权，**无语义召回**，同义/上位词问题（「周报」vs「本周进展」）召回率为零。
3. **上下文拼装粗糙**：`ask` 把 top-8 片段直接 `map` 成 `### [[name]]\n片段` 拼进 system prompt；无「片段级定位」「引用可点回」「去冗余」机制，相关片段可能淹没在不相关片段中。
4. **时间维度与语义维度割裂**：`runTimeSummary` 按时间窗口捞全文、`ask` 按关键词捞片段，两条路径不复用同一召回层，无法「先按时间收敛、再按语义精排」。
5. **降级路径无 RAG**：`localFallback` 直接返回固定文案，无模型时 RAG 完全失效（仅 `ask` 非流式分支兜底）。

### 8.2 目标架构：统一 RAG 流水线

```
用户问题
  └─ [Router] 路由/规则判定（#9 已做）
       └─ [Retriever] 统一召回层
            ├─ FTS5 关键词召回（BM25）→ 候选片段
            ├─ 向量语义召回（embedding）→ 候选片段   ← 渐进引入
            └─ 时间/标签过滤（note_meta）→ 候选收敛
       └─ [Chunker] 笔记分块（标题/段落/列表级）
       └─ [Ranker] 重排（RRF 融合 + rerankHits 精排）→ top-K 片段
       └─ [ContextAssembler] 去冗 + 元信息包裹 + 引用锚点
       └─ [Generator] 模型生成（streamChat 真流式 #11）
       └─ [Citations] AIRefHit 回传，UI 可点跳
```

### 8.3 分块策略（Chunking）
- 新建 `note_chunks` 表（随 §1 FTS5 同库或 `index.db`）：

```sql
CREATE TABLE note_chunks (
  kb_id TEXT,
  note_path TEXT,
  chunk_idx INTEGER,
  chunk_text TEXT,
  heading TEXT,          -- 所属标题（面包屑）
  start_line INTEGER,
  end_line INTEGER,
  embedding BLOB,        -- Float32 向量（中期）
  PRIMARY KEY (kb_id, note_path, chunk_idx)
);
-- FTS5 仅索引文本，向量独立列避免 FTS 行膨胀
CREATE VIRTUAL TABLE note_chunks_fts USING fts5(
  kb_id UNINDEXED, note_path UNINDEXED, chunk_text,
  tokenize='unicode61'
);
```

- 分块规则（写入时由 §4 单通道触发，与索引同事务维护）：
  - 按 Markdown **标题层级**切分（H1/H2 为块边界）；
  - 单块超 `800` 字按段落再切；列表/表格整体保留；
  - 每块带 `heading` 面包屑（如 `项目/周报 > 本周进展`），提升可解释性。
- 取代现状「整篇读取 + 2KB 截断」：RAG 只取相关块，长笔记不再丢中部信息。

### 8.4 召回层（Retriever）
- **关键词召回**：`note_chunks_fts` 的 `bm25()`，复用 §1 的 FTS5 底座。
- **语义召回（渐进）**：`note_chunks.embedding` 与问题向量做余弦近邻（ANN）；先以 SQLite 扩展 `sqlite-vss` 试水，规模化后迁 LanceDB（见 §7/§10）。
- **收敛过滤**：`runTimeSummary` 改为「先 `note_meta.mtime >= sinceTs` 收敛候选集 → 再在候选集内做 FTS5/向量召回」，避免对全库无关笔记做语义计算（省成本、提精度）。
- **统一入口**：`ai-service.retrieve(kbId, query, {sinceDays?, tags?, topK?})` 返回 `ChunkHit[]`，`ask` 与 `runTimeSummary` 共用，消除双路径分裂。

### 8.5 重排（Ranker）
- **RRF 融合**：关键词分与语义分用 Reciprocal Rank Fusion 合并，避免量纲不一。
- **精排**：在 RRF 结果上跑现有 `rerankHits`（改为对 `chunk_text` 而非 `snippet` 计算词面重叠 + 标题/heading 加权），截断到 `topK`（默认 6–8）。
- **去冗余**：相邻块若 `heading` 相同且语义接近，合并或去重，控制 token。

### 8.6 上下文拼装与引用（ContextAssembler + Citations）
- 注入 prompt 的每段带锚点：`[[笔记名#标题]] @行号`，生成答案后 `AIRefHit.path` + `snippet` 回传 UI 可点跳（沿用现有 `AIRefHit`）。
- 拼装时按 `token` 预算（如 `6000`）贪心塞入 top 块，超限截断末位而非中部。
- `runTimeSummary` 的 `usage` 统计保留（成本控制 #9/#10 已做）。

### 8.7 降级 RAG
- 无模型时：`localFallback` 改为返回「关键词命中的 top 块摘要」（纯本地），而非固定文案；保证无网/无 key 时 RAG 仍可给出基于检索的有限答案。

### 8.8 影响面
- 新增 `rag-service.ts`（编排 Retriever/Ranker/Assembler）；`ai-service.ask/askWithHistory/askStream` 与 `runTimeSummary` 改为调用 `ragService.retrieve`。
- `SearchResult.snippet` 缓存前 8KB 逻辑废弃，改为读 `note_chunks`。
- `kb_search` 工具改为返回 `ChunkHit`（带 `heading`），对 agent 更友好。
- 对外契约不变（`ask`/`askStream` 入参、返回结构不变）。

### 8.9 优先级
- **P0 必做**：§8.3 分块 + §8.4 统一召回入口 + §8.5 RRF+精排 + §8.6 引用锚点 —— 直接修复「长笔记截断 / 双路径分裂 / 引用不可点」，是 RAG 稳定性与质量底座。
- **P3 增强**：§8.4 向量语义召回、§8.7 降级 RAG。

## 9. 重构落地顺序与兼容性

| 阶段 | 内容 | 稳定性收益 | 扩展性收益 |
| --- | --- | --- | --- |
| **S1（P0）** | §4 写入单通道+自愈；§1 FTS5 落盘+增量+异步；§8.3/8.4/8.5/8.6 RAG 分块+统一召回+重排+引用 | 消除索引/文件不一致、重启全扫、搜索阻塞；消除长笔记截断与双路径分裂 | 检索/语义可扩展到大库 |
| **S2（P1）** | §2 链接索引持久化；§3 元数据/标签/时间 SQL 化 | 反链重启可用、watch 丢事件自愈 | 时间/标签组合检索 |
| **S3（P2）** | §6 按库分库；§5 会话追加写 | 单库隔离、备份可迁移 | 多库规模化 |
| **S4（P3）** | §7 向量底座 + §8.4 语义召回 + §8.7 降级 RAG | 无网/无 key 仍可用 RAG | 语义检索 |

**兼容策略**：
- 旧版内存索引随 §1 废弃；首次启动对已有 KB 自动 `reindex` 写入 FTS5（一次性，可后台）。
- `note_path` 作为跨层稳定主键，所有表以 `(kb_id, note_path)` 关联，重构不破坏现有路径约定。
- 对外 IPC 通道（`kb_search` / `kb_read_note` / `kb_list_notes` / 会话读写）签名不变，仅内部实现替换；新增 `rag-service` 为内部编排，不影响 skill/路由层。

## 10. 风险与回滚

- **FTS5 依赖**：`better-sqlite3` 需编译期启用 FTS5（多数预编译二进制已带；若缺则启用 `SQLITE_ENABLE_FTS5` 重新构建或换 `node-sqlite3`）。验证：`PRAGMA compile_options` 含 `ENABLE_FTS5`。
- **reindex 耗时**：大库首次全量建 FTS + 分块可能数秒～数十秒，放后台并展示进度，不阻塞 UI。
- **向量扩展依赖**：`sqlite-vss` 需原生模块；若不可用，§8.4 语义召回降级为仅关键词（RAG 仍可用），不阻断主流程。
- **回滚**：旧内存索引代码保留一个 `LegacySearchService` 分支，FTS 异常时可开关回退；`config.db`/`index.db` 表结构向后兼容（新增表，不改旧表）。

---

## 11. 结论

当前存储以「文件为真源 + 内存派生索引」为主，写入原子化已具备基础稳定性；RAG 侧的主要短板在**无分块（长笔记被截断）、双路径召回分裂、纯关键词无语义、引用不可点**。

重构以 **FTS5 落盘 + 单通道写入 + 增量 watch 维护（§1/§4）** 为存储底座，叠加 **统一 RAG 流水线（§8：分块 → FTS5/向量统一召回 → RRF+精排 → 引用锚点）** 为核心，即可同时拿下稳定性（索引不丢、长笔记完整、引用可溯源）与扩展性（语义召回、大库、多库）两块；向量检索与按库分库作为后续增强，接口契约全程向后兼容。
