# 锦囊笔记 · 插件系统实现方案

> 版本：v1.0（草案）
> 目标：为 ForgeNote 设计一套类 Obsidian 的插件扩展体系，让第三方（以及用户自己）能够扩展知识库能力、AI 能力与界面，而无需修改应用主干代码。
>
> 前置文档：
> - `doc/AI调用重构技术方案.md` —— AIHub / Skill 注册表 / MCP 工具运行时
> - `doc/MCP技术实现方案.md` —— Confirm-then-Act 确认-执行框架
> - `doc/AI智能管家重构方案.md` —— Skill 收敛、批量任务、巡检
> - `doc/笔记版本实现方案.md` —— 版本服务与 `.forge/` 目录约定

## 1. 背景与目标

### 1.1 为什么要做插件

当前 ForgeNote 的能力扩展存在一个结构性矛盾：**每加一个能力都要改主干代码**。

以已落地的「知识库体检」为例，新增它需要改动：`patrol-service`（新建）+ `ipc-channels` + `ipc.ts` + `preload` + `DiagnosePage` + `PatrolReportCard` 共 6 处。这种模式的代价是：

| 问题 | 表现 |
|---|---|
| 主干膨胀 | 每个小众需求都进主干，代码越来越臃肿 |
| 无法定制 | 用户想要的能力只能等官方排期 |
| 生态为零 | 无法借助社区力量扩展 |

### 1.2 设计目标

| 维度 | 目标 |
|---|---|
| 能力完整 | 插件能扩展 AI 能力、知识库操作、界面与编辑器 |
| 安全可控 | 权限声明 + 用户确认，恶意插件无法静默窃取数据 |
| 稳定兼容 | 插件 API 版本化，主应用升级不轻易破坏插件 |
| 低门槛 | 一个 `manifest.json` + 一个 `main.js` 即可跑起来 |
| 复用现有 | 建立在 Skill / MCP 工具 / ConfirmableAction 之上，不另起炉灶 |

### 1.3 非目标

- 不做进程级沙箱（不引入 `vm2` / `isolated-vm`），改用「权限声明 + 信任模型」，与 Obsidian 一致
- 不做云端插件市场（阶段五只做可选的静态索引，不建服务器）
- 不做插件间依赖管理（v1 各插件独立）

## 2. 借鉴 Obsidian：学什么、不学什么

### 2.1 Obsidian 插件模型的精髓

| 机制 | 说明 | 我们是否采用 |
|---|---|---|
| `manifest.json` 声明元数据 | id / name / version / minAppVersion | 采用 |
| `onload()` / `onunload()` 生命周期 | 插件自己管理资源与清理 | 采用 |
| **命令面板（Command Palette）** | 插件注册命令，统一入口调用 | **采用，且作为首选扩展点** |
| 事件钩子（vault.on('modify') 等） | 监听应用内事件 | 采用 |
| `registerEditorExtension` | 直接挂 CodeMirror 6 扩展 | 采用（本项目编辑器正是 CodeMirror 6） |
| 插件数据 API（loadData/saveData） | 插件私有持久化 | 采用 |
| 设置页（Plugin Setting Tab） | 插件自带配置项 | 采用 |
| 单一渲染进程内运行 | 插件即渲染层 JS | **不采用**（本项目安全模型不同，见 §3） |

### 2.2 关键差异：Obsidian 是单进程，我们不是

Obsidian 基于 Electron 但关闭了 `contextIsolation` 并开启 `nodeIntegration`，插件可以直接 `require('fs')`。

**ForgeNote 的安全配置更严格**（`src/main/index.ts:43-48`）：

```ts
webPreferences: {
  preload: join(__dirname, '../preload/index.js'),
  contextIsolation: true,     // 隔离上下文
  sandbox: false,             // 仅主进程侧关闭沙箱
  nodeIntegration: false      // 渲染层无 Node 能力
}
```

这带来一个**必须承认的约束**：

> 渲染层插件**不能** `require` 任何 Node 模块，只能通过 `contextBridge` 暴露的 `window.forge.*` 操作应用。

因此本方案采用**双入口插件模型**（§5.2）：主进程入口做「能做的事」，渲染层入口做「界面的事」。这比 Obsidian 复杂一点，但安全性显著更好。

## 3. 现状梳理

### 3.1 已有扩展机制盘点

项目里其实已经有 5 套「注册表」，插件系统应建立在它们之上：

| 机制 | 位置 | 注册方式 | 插件可用 |
|---|---|---|---|
| **Skill** | `skill-engine.ts:414` `SKILLS` | 字面量对象，无 register API | 需补 API |
| **MCP 工具** | `tool-runtime.ts:36` `KB_TOOLS` | 数组，无 register API | 需补 API |
| **确认操作** | `confirmable-action-service.ts` | 已有 `register(type, handler)` | 可直接复用 |
| **Agent 人格** | `agents/registry.ts` | 已有 registry | 可直接复用 |
| **外部 MCP 服务** | `mcp-client.ts`（stdio / SSE） | 配置驱动 | 可作为进程外插件通道 |

**关键缺口**：`SKILLS` 与 `KB_TOOLS` 都是**字面量常量**，没有注册函数。插件要扩展它们，必须先把这两处改造为「注册表 + register API」。

### 3.2 界面扩展点现状

| 扩展点 | 现状 | 改造难度 |
|---|---|---|
| 主菜单 `MainMenuRail.tsx:16` | `const items: MenuItem[]` 硬编码数组 | 低：改为「内置项 + 注册项」合并 |
| 页面路由 `App.tsx:110-119` | `mainView` 的 11 个分支硬编码 | 中：`MainView` 是联合类型，需扩展为 `MainView \| string` 或开放注册 |
| 右侧面板 `RightPanel.tsx` | `panelTab` 三态 + 硬编码 PanelCard | 低：加 slot 渲染数组 |
| 编辑器 `NotePane.tsx:210` | CodeMirror `extensions` 数组 | 低：暴露 registerEditorExtension |
| 设置页 `SettingsPage.tsx` | 分区硬编码 | 中：加插件设置 Tab |

### 3.3 事件机制现状

`src/main/utils/event-bus.ts` 全文只有 4 行，是一个裸 `EventEmitter`：

```ts
import { EventEmitter } from 'events';
export const eventBus = new EventEmitter();
```

**存在两个问题需要顺带修复**（否则插件无法正确使用事件）：

1. **无类型约束**：无事件名常量表、无 payload 类型。建议升级为泛型事件映射。
2. **payload 缺 `kbId`**：`fsChange` 的 payload 只有 `{ type, path, isDir?, to? }`，而 `watcher.ts` 闭包里其实持有 kbId。多知识库场景下插件无法区分事件来源。

### 3.4 需要新增的基础设施

| 缺口 | 说明 |
|---|---|
| 插件清单格式 | `manifest.json` schema |
| 插件加载器 | 主进程 `require` 外部 JS |
| 渲染层插件注入 | 在隔离上下文中执行插件 UI 代码 |
| 权限系统 | 声明式权限 + 用户确认 |
| 插件私有存储 | 每个插件独立的数据文件 |
| 插件管理 UI | 列表、启用/禁用、权限确认、设置 |

## 4. 设计目标架构

```
┌──────────────────────────── 渲染进程（隔离上下文，无 Node） ────────────────────────────┐
│  插件 UI 入口 ui.js                                                                      │
│   · 只能访问 window.forge.*（contextBridge 暴露）与 DOM                                  │
│   · 通过 UI 插槽挂界面：侧栏卡片 / 菜单项 / 设置 Tab / 状态栏 / 编辑器扩展                │
└──────────────────────────────────┬──────────────────────────────────────────────────────┘
                                   │ IPC（动态通道 plugin:<id>:*）
┌──────────────────────────────────▼────────────────────────────── 主进程（Node 环境） ───┐
│  PluginHost（插件宿主）                                                                   │
│   ├─ ManifestLoader   读取 / 校验 manifest.json                                          │
│   ├─ PermissionGate   权限声明 → 用户确认 → 生成受限 API                                 │
│   ├─ ModuleLoader     require(main.js)，捕获加载错误不影响主应用                          │
│   ├─ Lifecycle        onload / onunload，插件崩溃自动禁用                                │
│   └─ ApiFactory       按权限装配 forge API 对象                                          │
│                                                                                          │
│  扩展点注册表（全部由插件贡献）                                                           │
│   ├─ SkillRegistry   ← 新增 registerSkill（改造 SKILLS）                                 │
│   ├─ ToolRegistry    ← 新增 registerTool（改造 KB_TOOLS）                                │
│   ├─ ActionRegistry  ← 复用 actionService.register                                       │
│   ├─ CommandRegistry ← 新增（命令面板）                                                  │
│   ├─ EventHooks      ← 复用 eventBus（需补 kbId 与类型）                                 │
│   └─ UiSlots         ← 新增（渲染层插槽清单）                                            │
│                                                                                          │
│  落盘：                                                                                   │
│   · 全局插件  <userData>/plugins/<pluginId>/                                              │
│   · 插件数据  <userData>/plugin-data/<pluginId>/data.json                                │
│   · KB 级启用状态  <kbRoot>/.forge/plugins.json                                          │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 关键决策：插件装在哪里

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 知识库内（`.forge/plugins/`） | 跟着知识库走，换电脑同步 | 知识库目录被污染；多个 KB 重复安装 | 不选 |
| 应用级（`userData/plugins/`） | 装一次全局可用；不含业务数据 | 换电脑需重装 | **采用** |
| 两级结合 | 兼顾 | 复杂度高 | v1 不做 |

**启用粒度**：插件全局安装，但**按知识库启用**。启用状态记在 `<kbRoot>/.forge/plugins.json`，这样用户可以在「工作知识库」启用工作相关插件，在「私人知识库」不启用。这与 Obsidian 的 vault 级启用一致。

## 5. 插件清单与目录结构

### 5.1 目录结构

```
<userData>/plugins/
└─ forgenote-daily-review/          # 目录名即 pluginId
   ├─ manifest.json                 # 必需
   ├─ main.js                       # 必需：主进程入口（Node 环境）
   ├─ ui.js                         # 可选：渲染层入口（隔离环境）
   └─ README.md                     # 可选
```

### 5.2 manifest.json

```json
{
  "id": "forgenote-daily-review",
  "name": "每日回顾",
  "version": "1.0.0",
  "description": "每天自动生成昨日笔记回顾",
  "author": "your-name",
  "minAppVersion": "1.3.0",
  "apiVersion": 1,
  "main": "main.js",
  "ui": "ui.js",
  "permissions": [
    "fs:read",
    "fs:write",
    "ai:call",
    "ui:sidebar",
    "storage"
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 全局唯一，建议 `作者-功能` 命名 |
| `version` | 是 | 语义化版本 |
| `minAppVersion` | 是 | 低于此版本拒绝加载，避免 API 不兼容 |
| `apiVersion` | 是 | 插件 API 大版本，宿主据此适配 |
| `main` | 是 | 主进程入口，相对插件目录 |
| `ui` | 否 | 渲染层入口；缺省表示纯后台插件 |
| `permissions` | 是 | 声明式权限，见 §8 |

### 5.3 权限清单

| 权限 | 允许做什么 | 风险等级 |
|---|---|---|
| `fs:read` | 读取知识库笔记与目录树 | 低 |
| `fs:write` | 创建/修改/删除/移动笔记 | 高 |
| `ai:call` | 调用已配置的 AI 模型（会产生费用） | 中 |
| `ai:tool` | 注册 MCP 工具供 AI 调用 | 中 |
| `ai:skill` | 注册 Skill（AI 能力） | 中 |
| `ui:*` | 各类界面插槽 | 低 |
| `storage` | 插件私有持久化存储 | 低 |
| `network` | 发起外部网络请求 | **高**（v1 默认不授予，需显式二次确认） |
| `shell` | 启动子进程 | **高**（v1 不开放） |

## 6. 生命周期

### 6.1 主进程入口 main.js

```js
// 插件主进程入口（CommonJS，Node 环境）
module.exports = {
  async onload(forge, ctx) {
    // 注册一个 AI 可调用的工具
    forge.ai.registerTool({
      name: 'daily_review_generate',
      description: '生成指定日期的笔记回顾',
      input_schema: {
        type: 'object',
        properties: { date: { type: 'string' } },
        required: ['date']
      }
    }, async (args, toolCtx) => {
      const notes = await forge.fs.listNotes(toolCtx.kbId, { sinceDays: 1 });
      return { count: notes.length, titles: notes.map(n => n.title) };
    });

    // 注册命令（出现在命令面板）
    forge.commands.register('daily-review.run', {
      title: '生成昨日回顾',
      async handler(ctx) {
        const kbId = ctx.kbId;
        const result = await forge.ai.run({ skill: 'ask', input: { text: '总结昨天的笔记' }, kbId });
        forge.ui.toast({ level: 'success', text: '回顾已生成' });
      }
    });

    // 监听文件变更
    ctx.events.onFsChange((e) => {
      if (e.type === 'change') console.log('笔记变更：', e.path);
    });
  },

  async onunload(forge, ctx) {
    // 宿主会自动撤销本插件注册的所有能力，这里只清理自己的资源
  }
};
```

### 6.2 生命周期时序

```
应用启动
  → PluginHost.scan()            扫描插件目录，读取 manifest
  → 校验：id 冲突 / minAppVersion / apiVersion / manifest 必填字段
  → 读取 KB 级启用状态 .forge/plugins.json
  → 对已启用插件：
       PermissionGate 检查权限是否已授权
         未授权 → 记录待确认，不加载（在设置页提示）
         已授权 → ModuleLoader.require(main.js)
                  → 按权限装配 forge API
                  → await onload(forge, ctx)
                  → 成功：标记 active
                  → 失败/超时：标记 error，自动禁用，不影响其它插件与主应用
  → 渲染层就绪后：注入 ui.js（按插件顺序）
```

### 6.3 崩溃隔离

- `onload` 包在 try/catch 内，单插件失败不影响其它插件与主应用
- `onload` 超过 5 秒未完成视为超时，强制标记失败
- 插件注册的扩展点全部登记在「插件 → 贡献项」映射表中，`onunload` 或崩溃时**批量撤销**，避免残留

## 7. 扩展点（Contribution Points）

这是插件系统的核心。按「能力域」分组：

### 7.1 AI 能力域

| 扩展点 | API | 说明 |
|---|---|---|
| 注册 Skill | `forge.ai.registerSkill(skill)` | 新增一个 AI 能力，可被 AIHub 路由、被模型自路由选中 |
| 注册 MCP 工具 | `forge.ai.registerTool(tool, handler)` | 工具进入 `tool-list`，AI 在推理中可自主调用 |
| 注册 Agent 人格 | `forge.ai.registerAgent(agent)` | 新增专家角色 |
| 注册确认操作 | `forge.actions.register(type, handler)` | 复用 `actionService`，写操作走确认流 |

**为什么插件注册的工具也能被 AI 调用**：`tool-runtime` 的 `executeTool` 目前按 `name` 分派。改造为「内置 + 插件」两级查找后，插件工具与内置工具对模型完全等价——这是让插件能力真正融入 AI 工作流的关键。

### 7.2 知识库操作域

| 扩展点 | API |
|---|---|
| 读取笔记 | `forge.fs.readNote(kbId, path)` |
| 写入笔记 | `forge.fs.writeNote(kbId, path, content)`（需 `fs:write`） |
| 列举/搜索 | `forge.fs.listNotes` / `forge.search.query` |
| 版本历史 | `forge.version.list` / `restore` |
| 批量操作 | `forge.actions.create({ type: 'batchPatch', ... })` |

### 7.3 命令与事件域

| 扩展点 | API | 说明 |
|---|---|---|
| 注册命令 | `forge.commands.register(id, { title, hotkey?, handler })` | 统一进入命令面板（Cmd/Ctrl+P） |
| 文件变更 | `ctx.events.onFsChange(cb)` | 复用 eventBus |
| 应用事件 | `ctx.events.on(event, cb)` | 笔记打开/关闭、KB 切换等 |
| 定时任务 | `forge.schedule.every(cron, handler)` | 可选，阶段三提供 |

> **命令面板是首选扩展点**。理由：它不需要插件理解 React 或布局，一个 `title` + `handler` 就能让能力被用户触达，是投入产出比最高的入口。

### 7.4 界面域（渲染层插槽）

| 插槽 | API | 挂载位置 |
|---|---|---|
| 侧栏卡片 | `forge.ui.registerSidebarPanel({ title, render })` | RightPanel 属性区 |
| 主菜单项 | `forge.ui.registerMenuItem({ id, icon, label })` | MainMenuRail |
| 自定义页面 | `forge.ui.registerView({ id, title, render })` | 主内容区（扩展 mainView） |
| 设置 Tab | `forge.ui.registerSettingTab({ id, title, render })` | SettingsPage |
| 状态栏项 | `forge.ui.registerStatusBarItem({ render, position })` | StatusBar |
| 编辑器扩展 | `forge.ui.registerEditorExtension(extension)` | CodeMirror extensions |
| 笔记工具栏 | `forge.ui.registerNoteToolbarButton({...})` | NotePane 顶部 |

**渲染层入口 ui.js 的形态**：

```js
// ui.js —— 运行在隔离上下文，只能通过 window.forge 操作应用
module.exports = {
  onload(forge) {
    forge.ui.registerSidebarPanel({
      id: 'daily-review-panel',
      title: '今日回顾',
      render(container) {
        container.innerHTML = '<div class="dr-panel">加载中…</div>';
        forge.fs.listNotes(forge.kb.getActive().id, { sinceDays: 1 })
          .then(notes => {
            container.querySelector('.dr-panel').textContent = `昨日 ${notes.length} 篇笔记`;
          });
      }
    });
  }
};
```

**关于 React 的说明**：v1 **不暴露 React 给插件**。插槽 `render(container)` 接收一个 DOM 容器，插件用原生 DOM 或自带框架渲染。这样避免插件与主应用的 React 版本耦合——这是长期兼容性的关键取舍（Obsidian 暴露了 React，代价是插件与宿主版本强绑定）。

### 7.5 编辑器扩展（CodeMirror 6）

`registerEditorExtension` 是最有价值的界面扩展点之一。由于 `NotePane` 用的正是 CodeMirror 6，插件可以直接复用官方扩展：

```js
forge.ui.registerEditorExtension(
  forge.codemirror.decorations.compute(...)  // 由宿主注入 CodeMirror 模块
);
```

**实现要点**：插件无法 `require('@codemirror/view')`（渲染层无 Node）。因此宿主要把常用的 CodeMirror 模块通过 `forge.codemirror.*` 暴露给插件，插件只做组合。暴露范围控制在：`view` / `state` / `language` 三个包的常用导出。

## 8. 安全与权限

### 8.1 威胁模型（诚实面对）

本项目主进程 `sandbox: false`，插件以 `require()` 载入主进程，**因此插件本质上拥有主进程的全部能力**。任何权限声明都无法从技术上阻止恶意插件绕过 API 直接 `require('fs')`。

这与 Obsidian 面临的处境完全相同。因此安全策略是**信任模型 + 降低风险**，而非技术沙箱：

| 层次 | 措施 |
|---|---|
| 安装前 | 展示权限清单，用户显式同意；高权限（`network` / `shell`）二次确认并标红 |
| 安装时 | 记录插件路径与 manifest 摘要；校验 `minAppVersion` |
| 运行时 | 按权限装配 API：未声明 `fs:write` 的插件，`forge.fs.writeNote` 直接抛错 |
| 可审计 | 插件对知识库的写操作全部记入 `audit-service`，可在「审计」页查看是哪个插件改的 |
| 可撤销 | 插件写操作建议走 `confirmable-action`，纳入版本历史，可回滚 |
| 兜底 | 一键禁用全部插件；安全模式启动（跳过所有插件） |

### 8.2 权限门的实现

```ts
// 按权限装配 API：未声明的能力根本不会出现在 forge 对象上
function buildApi(manifest: PluginManifest, granted: Set<Permission>): PluginAPI {
  const guard = (p: Permission, fn: unknown) =>
    granted.has(p) ? fn : () => { throw new Error(`插件 ${manifest.id} 未声明权限 ${p}`); };

  return {
    fs: {
      readNote: guard('fs:read', ...),
      writeNote: guard('fs:write', ...),
      // ...
    },
    // ...
  };
}
```

### 8.3 未来可选：进程外插件

若后续需要真正的隔离，可复用**已实现的 `mcp-client`（stdio / SSE）**：把插件打包为独立进程，通过 MCP 协议通信。此时插件只能调用宿主暴露的工具，天然沙箱化。

本方案把这条路径留作 §11 阶段五的可选项，v1 不实施。

### 9.2 主进程 API 全貌

```ts
interface PluginAPI {
  readonly apiVersion: number;
  readonly pluginId: string;

  /** 知识库操作 */
  fs: {
    readNote(kbId: string, path: string): Promise<NoteContent>;
    writeNote(kbId: string, path: string, content: string): Promise<void>;   // fs:write
    listNotes(kbId: string, opts?: { dirPath?: string; sinceDays?: number }): Promise<NoteInfo[]>;
    moveNote(kbId: string, from: string, toDir: string): Promise<string>;     // fs:write
    deleteNote(kbId: string, path: string): Promise<void>;                    // fs:write
  };

  /** 知识库元信息 */
  kb: {
    list(): Promise<KBSummary[]>;
    getActive(): Promise<KnowledgeBase | null>;
  };

  /** 检索 */
  search: {
    query(kbId: string, q: string, limit?: number): Promise<SearchHit[]>;
  };

  /** 版本历史 */
  version: {
    list(kbId: string, notePath: string): Promise<VersionListItem[]>;
    create(kbId: string, notePath: string, note?: string): Promise<string | null>;
    restore(kbId: string, notePath: string, versionId: string): Promise<{ ok: boolean; message: string }>;
  };

  /** AI 能力（需 ai:call / ai:tool / ai:skill） */
  ai: {
    run(req: AIRequest): Promise<AIResponse>;
    runStream(req: AIRequest, onToken: (d: string) => void): Promise<AIResponse>;
    registerTool(tool: MCPTool, handler: ToolHandler): void;
    registerSkill(skill: AISkill): void;
    registerAgent(agent: AgentDef): void;
  };

  /** 需确认的操作（写操作强烈建议走这里） */
  actions: {
    register(type: string, handler: ActionHandler): void;
    create(action: ConfirmableAction): void;   // 交给用户确认后执行
  };

  /** 命令面板 */
  commands: {
    register(id: string, cmd: { title: string; hotkey?: string; handler: (ctx: CommandCtx) => void | Promise<void> }): void;
  };

  /** 插件私有存储（storage） */
  storage: {
    get<T>(key: string, fallback?: T): Promise<T | undefined>;
    set(key: string, value: unknown): Promise<void>;
  };

  /** 提示 */
  ui: {
    toast(msg: { level: 'info' | 'success' | 'warn' | 'error'; text: string }): void;
  };
}
```

### 9.3 事件上下文

```ts
interface PluginContext {
  /** 插件目录绝对路径（读自己的资源文件用） */
  readonly dir: string;
  readonly manifest: PluginManifest;

  events: {
    /** 文件变更；kbId 由宿主补齐（见 §3.3） */
    onFsChange(cb: (e: FsChangeEvent) => void): () => void;
    /** 应用级事件 */
    on(event: 'note:open' | 'note:close' | 'kb:switch', cb: (payload: unknown) => void): () => void;
  };

  /** 日志：统一前缀，便于在日志中区分插件输出 */
  log: { info(...a: unknown[]): void; warn(...a: unknown[]): void; error(...a: unknown[]): void };
}
```

> 所有 `on*` 方法返回**取消订阅函数**，且宿主在 `onunload` 时会自动调用全部取消函数，避免插件忘记清理造成内存泄漏。

## 10. 需要改造的现有代码

插件系统不是从零搭建，而是要把现有「字面量常量」改造为「注册表」。

### 10.1 `skill-engine.ts` —— SKILLS 加注册 API

```ts
// 现状：export const SKILLS: Record<string, AISkill> = { ... }
// 改造：内置能力仍用字面量初始化，但增加注册/注销，并把插件 Skill 隔离存放

const pluginSkills = new Map<string, AISkill & { __pluginId: string }>();

export function registerSkill(skill: AISkill, owner?: string): void {
  if (SKILLS[skill.id]) throw new Error(`Skill ${skill.id} 已存在（内置），插件不可覆盖`);
  pluginSkills.set(skill.id, { ...skill, __pluginId: owner ?? '' });
}

export function unregisterSkillsByOwner(pluginId: string): void {
  for (const [id, s] of pluginSkills) if (s.__pluginId === pluginId) pluginSkills.delete(id);
}

export function getSkill(id: string): AISkill | undefined {
  return SKILLS[id] ?? pluginSkills.get(id);   // 内置优先，插件不可劫持内置能力
}
```

**关键设计**：内置优先、插件不可覆盖内置。避免恶意插件劫持 `ask` 等核心能力。

### 10.2 `tool-runtime.ts` —— 工具动态化

```ts
// 现状：export const KB_TOOLS: MCPTool[] = [...]；executeTool 内 switch(name)
// 改造：内置工具保留 switch 分支，未命中时查插件工具表

const pluginTools = new Map<string, { tool: MCPTool; handler: ToolHandler; owner: string }>();

export function registerTool(tool: MCPTool, handler: ToolHandler, owner?: string): void {
  if (tool.name.startsWith('kb_')) throw new Error('kb_ 前缀为内置保留');
  pluginTools.set(tool.name, { tool, handler, owner: owner ?? '' });
}

/** 供模型使用的完整工具清单（内置 + 插件） */
export function allTools(): MCPTool[] {
  return [...KB_TOOLS, ...[...pluginTools.values()].map(t => t.tool)];
}
```

`executeTool` 末尾加兜底分支：内置 switch 未命中 → 查 `pluginTools` → 仍未找到返回错误。

### 10.3 `eventBus` —— 补 kbId 与类型

```ts
// 现状：裸 EventEmitter，payload 无 kbId
// 改造：定义事件映射，并在所有 emit 点补 kbId

export interface AppEvents {
  fsChange: { kbId: string; type: FsChangeType; path: string; isDir?: boolean; to?: string };
  'note:open': { kbId: string; notePath: string };
  'note:close': { kbId: string; notePath: string };
  'kb:switch': { kbId: string };
}
```

> 需要同步修改 `watcher.ts` 的 5 处 emit 与 `fs-service.ts` 的 12 处 emit，把闭包中的 kbId 放进 payload。这是独立的小重构，建议单独一个 PR 完成。

### 10.4 类型扩展：`MainView`

```ts
// 现状（layout-store.ts:5）
export type MainView = 'note' | 'graph' | ... | 'diagnose';

// 改造：允许插件视图
export type BuiltinView = 'note' | 'graph' | ... | 'diagnose';
export type MainView = BuiltinView | (string & {});   // 保留字面量提示，同时接受任意字符串
```

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 恶意插件窃取/破坏数据 | 严重 | 权限声明 + 用户确认 + 审计可追溯 + 一键禁用 + 安全模式；明确告知用户「插件拥有完整主进程权限」 |
| 插件拖慢启动 | 体验 | `onload` 5 秒超时；异步并行加载；启动耗时超阈值时提示可禁用 |
| 插件崩溃带崩应用 | 严重 | try/catch 隔离 + 失败自动禁用 + 崩溃后下次启动询问是否重新启用 |
| API 演进破坏老插件 | 兼容 | `apiVersion` 版本化 + 适配层；`minAppVersion` 拒绝不兼容加载 |
| 插件与内置能力冲突 | 功能异常 | 内置优先、插件不可覆盖；`kb_` 前缀保留给内置工具 |
| 渲染层插件破坏 UI | 体验 | 插槽渲染包错误边界（React ErrorBoundary），单插槽崩溃不影响其它 |
| 编码门槛高 | 生态起不来 | 提供示例插件脚手架；命令面板等低门槛扩展点优先落地 |

### 附录 C · 与 MCP / Skill 的关系

| 机制 | 运行位置 | 用途 | 谁能写 |
|---|---|---|---|
| **Skill** | 主进程（内置） | 一个 AI 能力单元（Prompt + 逻辑） | 官方 / 插件 |
| **MCP 工具** | 主进程或外部进程 | 供模型在推理中调用 | 官方 / 插件 / 外部 MCP 服务 |
| **外部 MCP 服务** | 独立进程（stdio / SSE） | 接入第三方能力（日历、数据库等） | 任意第三方 |
| **插件** | 主进程 + 渲染层 | 完整扩展：能力 + 界面 + 命令 + 事件 | 任意第三方 |

**关系**：插件是「容器」，Skill / MCP 工具 / Action 是插件可贡献的「内容」。一个插件可以同时注册多个 Skill、多个工具、多个 UI 插槽。

已实现的 `mcp-client` 与插件并不冲突：前者面向「跨进程、跨语言」的外部服务，后者面向「应用内、深度集成」的扩展。阶段五可让插件以 MCP 协议跑在独立进程，兼顾两者优势。
