# 锦囊笔记 · 笔记版本管理实现方案

> 版本：v1.0（草案）
> 目标：为笔记提供完整的版本记录能力——自动留存历史版本、可视化比对差异、一键恢复到任意历史版本，并支持手动打点与版本清理。
>
> 前置文档：
> - `doc/MCP技术实现方案.md` —— Confirm-then-Act 确认-执行框架、笔记 Patch、快照机制
> - `doc/AI智能管家重构方案.md` —— 批量任务、执行后验证与回滚
> - `doc/多媒体实现技术方案.md` —— `.assets/` 资源管理约定

## 1. 背景与目标

### 1.1 当前痛点

| 问题 | 现状 |
|---|---|
| 误操作无法撤销 | `deleteNote` / `deleteDir` 为**硬删除**，无回收站 |
| AI 批量改坏无法回退 | 虽有 `notePatch` 回滚，但仅覆盖单次确认操作，且快照**仅存内存 1 小时** |
| 无法追溯修改过程 | `audit-service` 只记录「谁在什么时候做了什么操作」，不保存内容 |
| 长文写作无安全感 | 自动保存 500ms 防抖，历史内容被直接覆盖 |

### 1.2 设计目标

| 维度 | 目标 |
|---|---|
| 自动无感 | 用户正常写作即可产生版本，无需手动保存 |
| 可追溯 | 每个版本带时间、来源（手动/自动/AI/恢复前）、变更行数 |
| 可比对 | 任意两版本之间、以及版本与当前内容之间的 unified diff |
| 可恢复 | 一键恢复，恢复动作本身也产生一个版本（可再撤销） |
| 可控体积 | 存储占用有明确上限与淘汰策略，不随笔记数量线性膨胀 |
| 复用既有能力 | 复用 `atomicWrite`、`.forge/` 约定、`makeUnifiedDiff`、`syncIndex` |

### 1.3 非目标

- 不做多人协作 / 分支合并（单用户本地场景）
- 不做实时协同光标
- 不做云端同步

## 2. 现状梳理（可复用与需改造）

### 2.1 可直接复用的既有能力

| 能力 | 位置 | 复用方式 |
|---|---|---|
| `atomicWrite` | `src/main/utils/fs.ts` | 临时文件 + rename，保证快照写入不产生半截文件 |
| `.forge/` 目录约定 | `profile-service` / `session-store` / `patrol-service` / `inspire-history` | 版本数据落 `<kbRoot>/.forge/versions/` |
| `makeUnifiedDiff(before, after, context=2)` | `src/main/services/note-patch.ts:188` | 版本比对核心，**当前为模块私有，需导出**（见 §5.3） |
| `saveSnapshot` / `restoreSnapshot` | `src/main/services/note-patch.ts` | 短期回滚快照；版本管理是它的**持久化超集** |
| `syncIndex(kbId, notePath)` | `fs-service.ts:96` | 恢复后同步双链索引与 SQLite |
| `eventBus.emit('fsChange')` | 各写操作 | 恢复后通知渲染层刷新 |
| `auditService.record` | `audit-service.ts` | 版本创建/恢复写入审计 |
| `NotePane` 的 `lastSelfWriteRef` | `NotePane.tsx` | 已能区分「自己保存」与「外部/AI 修改」，可用于判定版本来源 |

### 2.2 需要改造或注意的现状

#### ⚠️ 陷阱 1：不能依赖 `birthtime` 判断文件创建时间

`atomicWrite` 采用 `writeFile(tmp) + rename(tmp → target)`，rename 会替换 inode，导致 `stat.birthtimeMs` 变成「最近一次写盘时间」。项目已因此在 FrontMatter 中固化 `createdAt`。

**推论**：版本时间戳必须自己记录，不能用文件 `birthtime` / `ctime` 推断。

#### ⚠️ 陷阱 2：自动保存 500ms 防抖，不能直接当版本

`NotePane.tsx:291-313` 的自动保存是 500ms 防抖，用户连续打字会触发数十次写盘。若每次写盘都存版本，单个笔记一天可产生上千个版本。

**推论**：版本创建必须**节流 + 内容去重 + 时间合并**（见 §4）。

#### ⚠️ 陷阱 3：重命名/移动/删除会丢失版本

版本目录若以笔记路径为键，重命名后路径变化会导致历史版本"失联"。

**推论**：版本需跟随笔记移动，删除时需明确策略（见 §4.5）。

#### 现有写操作清单（需在其中埋点）

| 方法 | 位置 | 是否需版本埋点 |
|---|---|---|
| `writeNote` | `fs-service.ts:115` | ✅ 主要埋点（正文变更） |
| `updateTags` / `updateSummary` | `fs-service.ts:178 / 197` | ✅ frontmatter 变更 |
| `writeText` | `fs-service.ts:478` | ✅（AI Patch 走此路径） |
| `moveNote` | `fs-service.ts:316` | ⚠️ 需迁移版本目录 |
| `renameNote` | `fs-service.ts:342` | ⚠️ 需迁移版本目录 |
| `deleteNote` | `fs-service.ts:305` | ⚠️ 需决定版本保留策略 |
| `deleteDir` | `fs-service.ts:425` | ⚠️ 递归删除，需批量处理 |
| `createNote` | `fs-service.ts:248` | ❌ 新建无历史 |

## 4. 关键设计决策

### 4.1 版本触发时机（核心难点）

同时支持四种触发来源，由 `source` 字段区分：

| 来源 | 触发条件 | 节流策略 |
|---|---|---|
| `auto` 自动 | 用户编辑后内容发生变化 | **静默期 3 分钟**：距上次版本超过 3 分钟且有内容变化才创建；3 分钟内的多次修改合并为一个版本 |
| `manual` 手动 | 用户点击「保存版本」 | 立即创建，可附备注 |
| `ai` AI 修改 | AI Patch / 批量任务执行前 | 立即创建（复用 `note-patch` 的 `saveSnapshot` 并持久化） |
| `pre-restore` 恢复前 | 用户恢复某版本前 | 立即创建当前内容的版本，保证恢复可撤销 |
| `pre-move` 移动/重命名前 | `moveNote` / `renameNote` 执行前 | 立即创建（路径变更属高风险操作） |

**为什么自动快照用「3 分钟静默期」而不是「停止输入 N 秒」**：

用户写作常有思考停顿，若用"停止输入 30 秒"会产生大量碎片版本。3 分钟静默期意味着「用户持续写作 1 小时 ≈ 20 个版本」，粒度适中且体积可控。

**实现要点**：调度器不在 `writeNote` 里同步执行（避免拖慢保存），而是记录 `pendingChange`，由定时器统一 flush。

### 4.2 内容去重

创建版本前先计算内容哈希，与最新版本哈希相同时**直接跳过**。这样：
- AI 改了 frontmatter 又改回来 → 不产生冗余版本
- 恢复后立即再恢复 → 不产生重复版本

### 4.3 存储结构

采用「按笔记分目录 + 索引与内容分离」：

```
<kbRoot>/.forge/versions/
├─ index.json                    # 全局索引：noteId ↔ notePath 映射 + 统计
└─ <noteId>/                     # noteId = sha1(notePath).slice(0,16)
   ├─ meta.json                  # 该笔记的版本元数据数组
   ├─ v_1735...a1.md             # 版本内容快照
   ├─ v_1735...b2.md
   └─ ...
```

**为什么用 `noteId`（路径哈希）而不是直接用路径做目录名**：

笔记路径可能包含 `/`、`空格`、`中文`、`（）` 等字符，直接做目录名会嵌套多层且可能有非法字符。用哈希做目录名可扁平化，同时在 `index.json` 保留 `noteId → notePath` 的反查映射。

**为什么不把内容塞进 `meta.json`**：meta 需要频繁读取（渲染版本列表），内容快照体积大。分离后列表加载只读 meta，按需读快照。

### 4.4 淘汰策略（RetentionPolicy）

三层约束，任一超限即触发淘汰（从最旧开始）：

```
1. 数量上限：单笔记最多 50 个版本
2. 时间分层：
   · 7 天内        → 全部保留
   · 7~30 天       → 每天保留最新 1 个
   · 30 天以上     → 每周保留最新 1 个
3. 体积上限：整个 .forge/versions/ 超过 KB 总大小的 20% 或 200MB 时，
   按「最旧优先」淘汰，直到降到阈值以下
```

淘汰在**版本创建后**异步执行，不阻塞主流程。

### 4.5 生命周期联动

| 事件 | 处理 |
|---|---|
| `moveNote` / `renameNote` | 更新 `index.json` 中该 `noteId` 对应的 `notePath`；**noteId 保持不变**（基于首次路径），因此内容目录无需移动 |
| `deleteNote` | 默认**保留版本数据**到 `.forge/versions/orphan/`，保留 30 天后清理；提供「连同版本一起删除」选项 |
| `deleteDir` | 递归处理目录下所有笔记，同上 |
| KB 删除 | 整个 `.forge/` 随之删除（版本数据与知识库同生命周期，符合直觉） |

> `noteId` 基于**首次纳入版本管理的路径**生成并终身不变，这是 move/rename 无需搬运内容目录的关键。

## 5. 数据模型

### 5.1 类型定义（`src/shared/types/version.ts`）

```ts
/** 版本来源 */
export type VersionSource =
  | 'auto'          // 自动快照（编辑静默期后）
  | 'manual'        // 用户手动保存
  | 'ai'            // AI 修改前
  | 'pre-restore'   // 恢复操作前（保证可撤销）
  | 'pre-move';     // 移动/重命名前

/** 单个版本元数据 */
export interface NoteVersion {
  /** 版本 id，格式 v_<时间戳36进制>_<随机> */
  id: string;
  /** 所属笔记 id（路径哈希，终身不变） */
  noteId: string;
  /** 创建时间（自记录，不能用 birthtime） */
  at: number;
  /** 版本来源 */
  source: VersionSource;
  /** 用户备注（仅 manual 来源有） */
  note?: string;
  /** 内容 sha1，用于去重与完整性校验 */
  hash: string;
  /** 内容字节数（UTF-8） */
  size: number;
  /** 相对上一版本的变更行数（+新增/-删除），首个版本为 null */
  delta?: { added: number; removed: number } | null;
}

/** 单笔记版本索引（meta.json） */
export interface NoteVersionMeta {
  noteId: string;
  /** 当前笔记路径（move/rename 时更新） */
  notePath: string;
  /** 笔记标题快照，删除后仍可显示可读名称 */
  title: string;
  versions: NoteVersion[];   // 按时间倒序（最新在前）
  updatedAt: number;
}

/** 全局索引（index.json） */
export interface VersionIndex {
  version: 1;
  /** noteId → 简要信息，避免遍历所有 meta.json */
  notes: Record<string, { notePath: string; title: string; count: number; lastAt: number }>;
}

/** 版本列表项（渲染层使用，含可恢复性标记） */
export interface VersionListItem extends NoteVersion {
  /** 快照文件是否仍存在（防止手工删除导致 UI 报错） */
  available: boolean;
}
```

### 5.2 版本内容快照

快照保存**完整原始文件内容**（含 frontmatter），与 `fs.readText` 读写格式一致。理由：

- 恢复时可直接 `atomicWrite` 写回，无需反向应用 diff
- diff 链路（正向增量）比 inverse-patch（反向增量）简单可靠得多
- 笔记体积通常在 KB 级，全量存储成本可接受

### 5.3 复用 `makeUnifiedDiff`

`note-patch.ts:188` 的 `makeUnifiedDiff` 目前是**模块私有函数**。方案要求：

1. 将其**上提**到 `src/main/utils/diff.ts` 并导出（同时保留 `note-patch.ts` 的引用）
2. 补一个结构化版本供 UI 渲染着色：

```ts
// src/main/utils/diff.ts
export function makeUnifiedDiff(before: string, after: string, context = 2): string;

export interface DiffLine {
  type: 'add' | 'del' | 'ctx';
  text: string;
  oldLineNo?: number;
  newLineNo?: number;
}

/** 结构化 diff，供渲染层渲染彩色行 */
export function structuredDiff(before: string, after: string, context = 2): DiffLine[];

/** 统计增删行数 */
export function diffStats(before: string, after: string): { added: number; removed: number };
```

> `makeUnifiedDiff` 已有大文档保护（行数组合 > 400 万时退化为统计摘要），上提时一并保留。

## 6. 主进程实现

### 6.1 新增 `src/main/services/version-service.ts`

```ts
class VersionService {
  /* ---------- 查询 ---------- */

  /** 列出某笔记的所有版本（读 meta.json + 校验快照存在性） */
  async list(kbId: string, notePath: string): Promise<VersionListItem[]>;

  /** 读取某版本的完整内容 */
  async getContent(kbId: string, notePath: string, versionId: string): Promise<string | null>;

  /** 读取某版本的元数据 */
  async getMeta(kbId: string, notePath: string, versionId: string): Promise<NoteVersion | null>;

  /* ---------- 写入 ---------- */

  /**
   * 创建版本。
   * @param opts.force 为 true 时跳过节流与去重（手动/AI/恢复前/移动前场景）
   * @returns 新版本 id，若被节流或去重跳过则返回 null
   */
  async create(
    kbId: string,
    notePath: string,
    opts?: { source?: VersionSource; note?: string; force?: boolean }
  ): Promise<string | null>;

  /** 删除指定版本 */
  async remove(kbId: string, notePath: string, versionId: string): Promise<void>;

  /** 执行淘汰策略 */
  async prune(kbId: string): Promise<{ removed: number; freedBytes: number }>;

  /* ---------- 恢复 ---------- */

  /**
   * 恢复：先为当前内容创建 pre-restore 版本，再写回目标版本内容。
   * 恢复后自动 syncIndex + emit fsChange，渲染层无需额外刷新。
   */
  async restore(
    kbId: string,
    notePath: string,
    versionId: string
  ): Promise<{ ok: boolean; message: string; restoreVersionId?: string }>;

  /* ---------- 生命周期 ---------- */

  /** move / rename 后更新 notePath 与 title */
  async onNoteMoved(kbId: string, fromPath: string, toPath: string): Promise<void>;

  /** 删除笔记：将版本数据转入 orphan 区，30 天后清理 */
  async onNoteDeleted(kbId: string, notePath: string): Promise<void>;

  /** 连同版本一起删除 */
  async purgeNote(kbId: string, notePath: string): Promise<void>;
}

export const versionService = new VersionService();
```

### 6.2 节流调度器

```ts
interface PendingChange {
  kbId: string;
  notePath: string;
  /** 首次检测到变化的时刻 */
  since: number;
  /** 最后一次变化的时刻 */
  lastChangeAt: number;
  timer?: NodeJS.Timeout;
}
```

规则：
- `recordChange(kbId, notePath)`（由 `writeNote` 调用，同步、开销极低）→ 更新 `pending`
- 定时器每 60s 巡检一次 `pending`，对满足「距上次版本 > 3 分钟 且 距最后变化 > 3 分钟」的条目执行 `create(source: 'auto')`
- 应用退出前 flush 所有 pending（避免最后 3 分钟的编辑丢失）

> 为什么用「定时巡检」而不是「每次写入 setTimeout」：写入极其频繁（500ms 防抖），频繁 clearTimeout/setTimeout 本身也是开销。定时巡检更稳。

### 6.3 埋点位置

| 位置 | 调用 |
|---|---|
| `fs-service.writeNote`（L115） | `versionService.recordChange(kbId, notePath)` |
| `fs-service.updateTags`（L178） | 同上 |
| `fs-service.updateSummary`（L197） | 同上 |
| `fs-service.writeText`（L478） | 同上 |
| `fs-service.moveNote`（L316） | 执行**前** `create({source:'pre-move', force:true})`，执行后 `onNoteMoved` |
| `fs-service.renameNote`（L342） | 同上 |
| `fs-service.deleteNote`（L305） | 执行后 `onNoteDeleted` |
| `fs-service.deleteDir`（L425） | 遍历 .md 逐个 `onNoteDeleted` |
| `confirmable-action-service` 的 `notePatch` / `batchPatch` | 执行**前** `create({source:'ai', force:true})` |

> **重要**：埋点调用必须是「失败不影响主流程」的，全部包 try/catch 静默吞错。版本功能是增值能力，不能因为版本写入失败导致笔记保存失败。

### 6.4 恢复流程

```
restore(kbId, notePath, versionId)
  ├─ 1. 读目标版本快照内容（缺失则返回失败）
  ├─ 2. 读当前内容
  ├─ 3. 内容相同 → 直接返回成功（无需恢复）
  ├─ 4. create({source:'pre-restore', force:true})    ← 保证可撤销
  ├─ 5. atomicWrite(abs(notePath), snapshotContent)
  ├─ 6. syncIndex(kbId, notePath)
  ├─ 7. auditService.record(kbId, 'confirmableAction', { type:'versionRestore', ... })
  └─ 8. eventBus.emit('fsChange', { type:'change', path: notePath })
```

第 8 步会让 `NotePane` 的 fs:change 监听收到通知。由于此时 `lastSelfWriteRef` 不匹配（不是编辑器自己写的），会走「外部修改」分支：若用户无未保存编辑则全量替换并保留光标——这正是期望行为。

```ts
  diff: (kbId: string, notePath: string, a: string, b: string) =>
    ipcRenderer.invoke(IPC.VS_DIFF, kbId, notePath, a, b) as Promise<DiffLine[]>,
  restore: (kbId: string, notePath: string, versionId: string) =>
    ipcRenderer.invoke(IPC.VS_RESTORE, kbId, notePath, versionId) as Promise<{ ok: boolean; message: string }>,
  create: (kbId: string, notePath: string, note?: string) =>
    ipcRenderer.invoke(IPC.VS_CREATE, kbId, notePath, note) as Promise<string | null>,
  remove: (kbId: string, notePath: string, versionId: string) =>
    ipcRenderer.invoke(IPC.VS_DELETE, kbId, notePath, versionId) as Promise<void>,
  prune: (kbId: string) =>
    ipcRenderer.invoke(IPC.VS_PRUNE, kbId) as Promise<{ removed: number; freedBytes: number }>,
}
```

> `VS_DIFF` 的 `a` / `b` 参数支持 `'current'` 作为特殊值，表示「与当前内容比对」，避免渲染层先取内容再传。

## 9. 与既有功能的集成

### 9.1 与 AI 修改的协同

`confirmable-action-service` 的 `notePatch` / `batchPatch` 在执行**前**创建 `ai` 来源版本。这意味着：

- 即使 AI 改坏了笔记，用户也能从版本历史回退到改之前
- 与现有的「回滚快照」（`saveSnapshot`，内存 1 小时）形成互补：
  - **回滚快照**：即时撤销，1 小时内有效，零 IO
  - **版本历史**：长期留存，可查看/比对任意历史点

### 9.2 与知识库诊断的协同

`patrol-service` 的巡检报告可增加一项：

> 「`.forge/versions/` 占用 45MB（占知识库 12%）」→ 一键清理

复用 `versionService.prune()` 与已有的 `confirmable-action` 框架注册一个 `pruneVersions` action。

### 9.3 与审计的协同

版本创建/恢复写入 `auditService`，使 `AuditPage` 能看到完整的「谁改了什么、何时恢复」链路。

> 注意：`auditService.record` 的 `action` 枚举当前为 `'move' | 'insertLink' | 'forge' | 'applyTemplate' | 'removeTemplate' | 'aiPatch' | 'confirmableAction'`。恢复操作复用 `'confirmableAction'` 并在 payload 中用 `type: 'versionRestore'` 区分（与既有 `batchPatch` 等做法一致），避免改动枚举影响既有查询。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 版本数据膨胀 | 磁盘占用失控 | 三层淘汰策略（§4.4）+ 巡检报告提示 + 手动清理入口 |
| 埋点拖慢保存 | 写作卡顿 | 埋点仅记录 pending（O(1) 内存操作），实际快照由定时器异步执行；全部 try/catch 静默 |
| 恢复覆盖未保存编辑 | 用户输入丢失 | 恢复前由 `NotePane` 的 fs:change 逻辑保护（有未保存编辑时不覆盖）；UI 恢复前二次确认并提示 |
| 快照与索引不一致 | 恢复后双链/检索失效 | 恢复后强制 `syncIndex`；`meta.json` 记录 hash 用于完整性校验 |
| 大笔记 diff 卡死 | UI 无响应 | `makeUnifiedDiff` 已有大文档保护；diff 渲染分页/截断 |
| 版本目录被手工删除 | 列表报错 | `list()` 检查快照存在性，返回 `available: false`，UI 置灰而非崩溃 |
| KB 备份时版本数据过大 | 备份体积膨胀 | 版本数据在 `.forge/` 内，备份工具可选择排除；设置项提供「备份时排除版本历史」开关（可选） |

### 14.2 与初稿的三处差异

1. **`DiffLine` 类型定义在 shared 而非 main**。初稿把 `structuredDiff` 放在 `src/main/utils/diff.ts`，类型也定义在那里。但 `src/shared/types/version.ts` 若从 main 引入类型，会导致渲染进程打包时引入主进程代码（`tsc -p tsconfig.web.json` 直接报 TS6307）。修正为：类型定义在 `@shared/types/version.ts`，`utils/diff.ts` 反向引入。

2. **preload 独立为 `version` 分组**。初稿把版本 API 挂在 `window.forge.version.*`，实现时一度误挂在 `ai` 分组下，已修正为独立分组，避免语义混淆。

3. **巡检的版本占用项默认不提示**。初稿未设阈值，改为占用超过 32MB 才出现在体检报告中——否则刚启用版本功能就会被这条提示打扰，而此时版本数据本身还很小。
